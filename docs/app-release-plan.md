# iOSアプリ化・オンライン機能計画

更新日：2026-10-16（日本時間）

本書は、ブラウザ版ASCENTを完成度向上後にiOSアプリとして公開するための計画をまとめる。会話で合意した仕様、採用候補の構成、未確定事項を区別する。ここに記した将来機能が、現在のコードやGCP環境へすべて実装済みという意味ではない。

## 1. 目的と進め方

- 現在のHTML／JavaScriptによるゲームを継続して調整し、将来iOSアプリとして公開する。
- 他ユーザーの存在をマップとステージ別ランキングで感じられるようにする。
- ゲーム内の名前とキャラクター配色を、そのユーザーの表示に使用する。
- 外部アカウント連携を必須としない。
- リアルタイム対戦・位置同期・常時接続は行わない。
- iOS化の前からバックエンドを構築し、現在のブラウザ版で通信と画面遷移を検証できる構成にする。
- iOS化後も同じバックエンドとスコア形式を使う。

## 2. 現在の実装と今後の変更

| 項目 | 現在 | 今後 |
| --- | --- | --- |
| プレイ記録 | コース別・レベル別の最新クリア記録を端末へ保存 | 同一条件・同一ユーザーにつきハイスコア1件だけ保存 |
| 計時 | 操作可能になった時点から開始し、結果で停止 | この基準を維持し、中断・復帰時のルールを追加 |
| 結果表示 | 中央モーダルに手数とタイムを表示 | ステージ別TOP5・本人のスコア・入賞表示を追加 |
| マップ | 自分の進捗とクリア記録を表示 | 他ユーザーの到達位置・キャラを人数制限付きで表示 |
| キャラエディット | ボディ1〜8段の横ストライプ、頭は単色。配色を端末へ保存 | プロフィールに配色を保存し、他ユーザーにも表示 |
| 初回配色 | 保存がなければボディの段数・各色・頭の色をランダム生成して保存 | この仕様を維持 |
| スタミナ | ステージ内の移動予算。ゲーム内左上の❤️で表示 | ライフと独立して維持 |
| ライフ・広告 | ローカルのライフ・ダミー広告を実装済み | 本番広告SDKとサーバー管理を追加 |
| オンライン基盤・引継ぎ | 未実装 | サーバーと端末側の共通処理を追加 |

既存の進捗・配色・記録を読み込める移行処理を用意し、更新のたびに初期化しない。旧記録には生成版・ルール版がないため、公開ランキングへの採用可否を決めるまで無条件に送信しない。

## 3. ユーザーとキャラクター

### 合意した方針

- 表示名はプレイヤーがゲーム内で設定する。
- 他サービスのアカウント名やプロフィールとは紐づけない。
- 他ユーザーのアイコンには、本人がキャラエディットで設定した頭・ボディの配色を使用する。
- 表示名ではなく、内部の専用ユーザーIDでスコアや進捗を識別する。

### 設計上の方針

- 表示用プロフィールと、本人確認用の認証情報を分ける。
- 名前の変更でスコアの所有者が変わらないようにする。
- 表示名・頭の色・ボディの色配列・コース別到達位置を、マップ表示に必要なプロフィールとして扱う。
- 他ユーザーへ認証情報や引継ぎ情報を公開しない。

表示名の文字数・使用可能文字・重複可否・公開時の不適切な名前への対応は未確定。

## 4. ステージ識別とハイスコア

### 確定した比較基準

1. 手数が少ない記録を優先する。
2. 同手数ならタイムが短い記録を優先する。

コース・ステージ・生成／ルール版・ユーザーごとにハイスコアを1件だけ保持する。再クリア時は、既存記録より良い場合だけ更新する。最新記録と自己ベストを別々に残したり、同じユーザーの複数プレイをランキングへ並べたりしない。

手数とタイムは、必ず同じプレイの組み合わせで保存する。異なるプレイの最少手数と最速タイムを合成しない。今回のプレイ結果を一時的に画面へ表示することは、複数の永続スコアを保持することとは分けて扱う。

### 比較条件を守るための識別情報

現在はレベル番号に基づくシードで生成するが、生成処理やルールの変更により、同じレベル番号でも条件が変わる。次の情報を記録・送信の共通形式へ含める。

| 情報 | 用途 |
| --- | --- |
| コースID | ノーマル／ロジハラを区別 |
| レベル番号 | マップ上のステージを識別 |
| 生成版・シード | 配置を再現し、生成変更を区別 |
| ルール版 | 可動域・吸着・スタミナ・ペナルティ等の変更を区別 |
| 内部ユーザーID | ハイスコアの所有者を識別 |
| 手数・経過時間 | スコアの比較 |
| 送信／プレイ識別子 | 再送時の二重処理防止 |

必要に応じ、生成された配置のハッシュも照合用に持つ。ただしハッシュだけをスコアの正当性証明として扱わない。

表示は現在の「n手 mm:ss:cc」（分:秒:1/100秒）を基本とする。保存は現在ミリ秒単位だが、順位比較も1/100秒へそろえるか、ミリ秒まで比較するかは未確定。完全同点の順位・表示順も合わせて決める。

## 5. マップとランキングの表示

### マップ上の他ユーザー

- 他ユーザーのキャラを、各ユーザーが到達したレベルのマスに表示する。
- マス単位・画面全体で表示数を制限する。
- 表示位置は保存された到達情報であり、オンライン中であることを意味しない。
- 起動時や特定のタイミングで取得・更新し、常時接続しない。

更新タイミングの候補は、起動時・マップ復帰時・クリア後。表示するユーザーの選出方法、具体的な人数上限、キャッシュの有効時間は未確定。

到達位置を「最高クリアレベル」とするか「次に挑戦できるレベル」とするかも未確定。現在の自分のマーカーと合わせる案は、次に挑戦できるレベルへの配置。

### レベルクリア後

- 中央の結果モーダルで、そのステージのTOP5と本人のスコアを表示する。
- 自分のハイスコアがTOP5内の場合は、入賞演出と何らかの褒賞を設ける。
- TOP5はユーザーごとのハイスコアを比較するため、同じユーザーが複数枠に並ばない。
- 自分がTOP5内の場合の本人欄の重複表示方法は、画面設計時に決める。

褒賞の内容・付与回数・判定時点・後から順位が下がった場合の扱いは未確定。「ステージ初回入賞で1回付与し、後から剥奪しない」は提案段階であり、確定仕様ではない。

### クリア済みレベルの再挑戦

- マップでクリア済みレベルをタップしたら、ゲーム開始前にTOP5と本人の保存済みハイスコアを表示する。
- そこからプレイ開始またはマップへ戻る操作を設ける。
- 未クリアレベルでは、この事前ランキング画面を表示しない。
- 事前ランキングの閲覧・通信待ち・広告表示をクリアタイムへ含めない。

## 6. ライフ

### 確定値

| 項目 | 値 |
| --- | --- |
| 初期ライフ | 3 |
| 上限 | 5 |
| 失敗時の消費 | 1 |
| 自然回復 | 30分ごとに1、自然回復上限3 |
| リワード広告の回復 | ライフ0で報酬成立時に1 |

- ライフはステージ内スタミナと別に管理する。現在の❤️表示をそのまま残機として流用しない。
- 自然回復はアプリを閉じている間も、保存した時刻から経過時間を計算する。
- 自然回復は3で止め、広告等の追加分を含む最大値は5。
- スタミナ切れによる失敗1回につき、ライフを1回だけ消費する。
- ライフ0ではステージ開始・リトライを止め、回復の案内を表示する方針。

ローカル版では通常ステージのみ適用し、途中退出／プレイ中RESTARTも1消費する。失敗直後のリトライは二重消費しない。デイリー・検証用コース・番号指定デバッグは対象外。自然回復の基準は3未満になった時刻とし、追加消費時も端数時間を維持する。端末時計の変更や通信再送でライフを増やせないよう、オンライン時はサーバー時刻とサーバー側の状態を基準にする設計を検討する。

## 7. 広告

| 種類 | 条件 | 表示・効果 |
| --- | --- | --- |
| 通常の全画面広告 | 5クリアごと | 結果とランキングの確認後、「次のステージへ」で移行する際に表示。ライフ回復はなし |
| リワード広告 | ライフ0で本人が選択 | 「広告を見てライフ＋1」を表示し、報酬成立時に1回復 |

- リワード広告は自動表示せず、プレイヤーが選ぶ。
- 広告を閉じたことではなく、広告SDKの報酬成立通知を回復の条件にする。
- 同じ広告報酬を複数回付与しない。
- 広告の取得・表示失敗や報酬未成立を、回復済みとして扱わない。
- リワード広告の直後に通常広告を重ねない方針。
- プレイ中・計時中には広告を挟まない。
- 広告SDKはゲーム本体から分離し、開発中はテスト用の広告処理へ差し替えられるようにする。

SDK／広告事業者は未選定。AdMobは候補。5クリアの数え方（再クリアを含むか）、未配信時の通常広告カウンター、連続広告を避ける具体的な間隔は未確定。入賞褒賞と広告によるライフ回復は別の処理として扱う。

## 8. 採用候補の構成

GCPを利用でき、iOS化前から現在のブラウザ版で接続・検証できる。次の構成を推奨案とする。サービス作成・プロジェクト設定・SDK導入は、この計画書作成時点では未実施。

| 要素 | 担当 |
| --- | --- |
| Cloud Run | 認証の確認、スコア受付と検証、ハイスコア更新、ランキング・マップ情報取得、褒賞・ライフ処理 |
| Firestore | ユーザー、配色、到達位置、条件別ハイスコア、ライフ・褒賞等の状態 |
| Firebase匿名認証 | 外部アカウント連携を求めないゲーム専用の本人識別 |
| 端末内保存 | 進捗・設定・配色・ハイスコア・取得済み情報・未送信データ |
| Capacitor | 現在のWebコードを活かすiOS化の候補。ネイティブ保存・広告・中断復帰との接続 |

- FirestoreはGoogle Cloudのサービスであり、FirebaseとGCPを別々のバックエンドとして二重に構築する計画ではない。
- 他の既存サービスへの影響を避けるため、ゲーム専用GCPプロジェクトへ分けることを推奨する。
- アプリはCloud RunのAPIへ通信し、サーバー側で権限や条件を確認してデータを読み書きする。
- Firebaseを利用しても、プレイヤーのGoogleアカウント連携は必須にしない。
- ブラウザ版とiOS版でバックエンド・記録形式を共用する。
- 現在のlocalStorageへの直接アクセスを共通の保存処理へ集約し、iOSではネイティブ保存へ差し替えられるようにする。Capacitor Preferencesは小規模な保存の候補。

### 通信と正当性

- 起動・マップ復帰・クリア後等に必要な情報だけ取得し、リアルタイム購読を必須にしない。
- 通信できなくても端末内でプレイを継続し、未送信スコアを後で再送できる構造にする。
- ハイスコア比較はサーバー側でも行い、再送・並行更新によって良い記録を悪い記録で上書きしない。
- 公開ランキングと褒賞は、サーバーで受理・判定した結果を正とする。キャッシュだけで入賞褒賞を確定しない。
- クライアントから送られた手数・タイムだけを無条件に信用しない。検証の強度と必要なログ量は別途設計する。
- 操作を再生する場合、本作ではキャンセル中の❤️取得も永続するため、確定位置の列だけでは不十分。ドラッグ途中・キャンセル・Undo・❤️取得も扱える記録形式が必要。
- 操作ログや再現検証だけで実時間の不正を完全に証明・防止できるとは扱わない。

## 9. 引継ぎと復旧

外部アカウントを使わないため、ブラウザ版からiOS版への移行・機種変更に使える引継ぎ機能を用意する必要がある。ブラウザ版とアプリ版で同じサーバーを使っても、端末の匿名認証情報が自動的に引き継がれるわけではない。

引継ぎ対象は、表示名、配色、到達レベル、条件別ハイスコア、ライフと回復の基準時刻、獲得済み褒賞等とする。端末だけのコピーではなく、同じゲーム内ユーザーとしてサーバー上の所有関係を維持する設計が必要。

### 提案中の方式（詳細未確定）

- 元端末で有効期限付き・1回限りの引継ぎコードを発行する。
- 移行先でコードを入力して本人確認し、同じゲーム内ユーザーへ接続する。
- 成功したコードは無効化し、再利用・同時実行による二重引継ぎを防ぐ。
- コードは十分な推測耐性を持たせ、サーバーではハッシュ等で保管し、試行回数を制限する。
- 前回の提案は複数端末同期ではなく「利用端末を移す」方式。旧端末の失効・排他利用を採用するかは未確定。
- 排他利用するなら、サーバー側でセッションの世代等を確認し、旧端末の操作が継続して受理されないようにする。
- 紛失時は元端末からコードを発行できないため、事前保管できる復旧キーも候補。採用の有無・再発行方法・漏えい時の対応は未確定。

内部ユーザーIDだけで本人確認を済ませたり、公開プロフィールのIDを引継ぎ用の秘密情報として使ったりしない。

## 10. 段階的な実装順序

| 段階 | 作業 | 確認すること |
| --- | --- | --- |
| 1. ゲーム側の基盤 | ステージ識別・版管理、ハイスコア1件化、保存／通信の共通処理、プロフィール | 不利な再クリアで上書きしない。旧保存を移行できる |
| 2. ローカルで画面検証 | 仮の他ユーザー、TOP5、再挑戦前表示、ライフ・広告のテスト用処理 | 未クリアでは事前ランキングを出さない。計時に閲覧・広告を含めない |
| 3. GCP接続 | 匿名認証、プロフィール、ハイスコア送信、TOP5・マップ情報の取得 | 別ユーザー識別、権限、再送、二重処理、オフライン復帰 |
| 4. 引継ぎ・運用 | 引継ぎ、必要なら復旧キー、褒賞とライフのサーバー管理 | 所有者が変わらない。コード再利用や二重付与を防げる |
| 5. iOS化 | Capacitor等の方式決定、ネイティブ保存、広告SDK、中断・復帰、実機調整 | セーフエリア、タッチ、ロック／着信、保存、性能、広告からの復帰 |
| 6. 公開前検証 | TestFlight、障害時の動き、公開用設定・ストア準備 | デバッグ記録・テスト広告を本番へ混ぜない |

アプリがバックグラウンドへ移った際のドラッグ解除・ポーズ保存と、クリアタイムを中断中も進めるかは、ランキング公開前に統一する。広告連携・公開要件は採用SDKと公開時点の公式要件で再確認する。

## 11. 次に決める事項

1. GCPプロジェクトと開発／本番環境の分け方。
2. ステージ・生成／ルール版の具体的なIDと、旧記録の扱い。
3. タイム比較単位、完全同点、入賞の判定時点と褒賞内容。
4. マップの到達位置定義、他ユーザーの選び方、表示数、更新間隔。
5. 表示名の制約、本人確認情報の保持方法。
6. 引継ぎ方式、旧端末との排他、紛失時の復旧手段。
7. 途中退出・RESTART時のライフ消費、回復時刻と広告カウンターの詳細。
8. オフラインでのライフ・スコア・褒賞の扱いと検証範囲。
9. バックグラウンド中の計時方針。
10. iOS化方式・広告SDK・公開前の実機テスト範囲。
