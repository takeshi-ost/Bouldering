# 共通記録世代（未公開候補）

## 境界

`js/score-metadata.js` の `RECORD_VERSION = 'r1'` が記録世代の単一クライアント定義。
アプリ版 `RELEASE_VERSION`、通常コース `COURSE_VERSION = 'v5'`、Dailyコース `DAILY_COURSE_VERSION = 'v4'` とは独立する。
`ONLINE_PROGRESS_VERSION` は互換フィールド名用の別名で、値は共通記録世代と同じ。

- 端末内進捗・成績・星・Daily記録/挑戦数/広告カウント・マップ報酬・公開同期チェックポイント・Web送信待ち・native送信待ちは、従来のキー末尾に `.r1` を付けた名前空間へ保存する。
- 進捗には `recordVersion`、成績/Daily/送信待ちスコアには `recordVersion` と元の `scoreSpecVersion` を保持する。世代やコース版を読込/再送時に補完しない。
- 新ランキングは `stageScores/r1_v5_existing_<stage>/entries/<uid>`。旧 `v5_existing_*` とは別ボード。
- 公開プロフィールは予約ボード `stageScores/r1_players/entries/<uid>`。`recordVersion` と `progressVersion` の両方を照合する。旧 `players/<uid>` は上書きしない。
- 予約プロフィールボードはスコアボードの検証に通らず、ランキングとして表示/投稿されない。既存の旧版削除処理が `stageScores/*/entries/<uid>` を全走査するため、新プロフィールも旧版から回収できる配置にしている。
- 起動前のチュートリアル既存ユーザー判定は、記録世代つき保存も認識する。既存ユーザー判定は記録の採用を意味しない。

新世代のキーがない場合は進捗0・星なし・Daily未達から始める。旧保存・旧ランキング・旧プロフィール・旧送信待ちは削除せず、元のまま残す。旧端末がオフライン中に書き足しても新しいキーには混ざらない。

## 同期・引継ぎ・報酬

Web/nativeとも保存前・キュー投入・キュー復元・再送・サーバー応答・表示で世代を確認する。新形式キュー内に混入した旧イベントも再ラベルせず保留する。nativeキューは世代別で、同じUIDを継続する。応答消失後の同一スコア再送はトランザクションで無変更として確認する。

引継ぎはトップレベル、進捗、入れ子成績、Daily、送信待ちを検証する。旧世代/世代なしのファイルは認証切替・保存操作前に拒否し、元ファイルも変更しない。nativeの既存の引継ぎ無効化方針は維持する。

ハート所持数・ライフは記録世代でリセットしない。そのため旧保存の**受取済み**報酬だけを権利証拠として参照し、同じマップ節目/同日のDaily報酬を再付与しない。旧クリアや旧未受取報酬を新世代の進捗・受取待ちとして採用しない。権利証拠は引継ぎの `rewardClaims` にも含める。広告、規約、Analyticsの状態はこの世代切替では変更しない。

これは端末内の報酬台帳であり、複数端末をまたぐサーバー管理の財布/厳密なexactly-once決済を新設したものではない。従来の報酬付与と所持数保存をまたぐ強制終了の完全な原子性も保証しない。リリース前に所持品も含む完全リセットを行う場合は、報酬権利の扱いも同時に明示する必要がある。

## 削除

削除時は恒久的な `accountDeletionLocks/<uid>` を先に作り、送信を停止してから、全ボードの自身の `entries` と従来の `players/<uid>` を削除し、Authは最後に削除する。予約プロフィールも同じ走査に含まれる。記録世代名の列挙や現行世代への限定を行わない。

端末削除は既知のゲームキーに加え、旧/現行/将来の `.r<number>` 記録キー、権利証拠、native送信待ちを掃除する。別アプリの保存、広告選択、規約/Analyticsのライフサイクルは既存専用処理の管轄のまま。新規の一括データ削除は実装・実行していない。

## ルール候補と適用順序

`firestore.rules` は**ローカル候補のみ**。サーバー側の世代は `currentRecordVersion()` の一箇所で定義する。

- 現行の記録世代と一致するスコア/プロフィールのみ書込み可能。recordVersionの欠落/null、コース版とボードの不一致、旧形式ボード、旧 `players` の作成/更新を拒否する。
- 全世代の自身の記録/プロフィール削除と、上限つき公開読取は維持する。恒久削除ロックは世代をまたいで書込みを止める。

公開作業を行う際の手順（今回は未実行）:

1. ローカル/CIのルール・クライアント回帰結果を確認する。旧アプリは更新後のルールで書込みを拒否されるため、更新必須案内/配布タイミングを決める。
2. ルール候補を先に適用して、新ボード/予約プロフィールへの許可を用意する。旧版書込みが止まるメンテナンス区間を設ける。現行公開ルールのまま新クライアントを出すと新パスへの書込みは拒否される。
3. 同じ記録世代を持つクライアントを配布する。オフライン起動、再接続、送信待ち、旧端末再接続、アカウント削除を実環境で確認する。
4. 将来世代を変える場合は `RECORD_VERSION` とルールの `currentRecordVersion()` を一致させ、アプリ版/コース版とは別の判断で更新する。
5. リリース前の実データリセットは、対象（Auth/旧プロフィール/全世代スコア/端末所持品/報酬権利/同意）とバックアップ・実行権限を別途確定してから行う。今回の変更はその削除を実行しない。

### 報酬の比較と修正

`followup/reward-comparison.json` は同一の隔離VMハーネスへ、記録世代導入前の報酬実装・初版の記録世代実装・追加修正版を読み込んだ比較結果。いずれも合成保存のみを使用し、実アカウントや実データへは書き込まない。

- **今回増えていた問題（修正済み）**: 引継ぎ先に `.reward-claims.v1.r1` の権利証拠だけがあり、元の成績/報酬ファイルがない場合、r2への切替で受取済みを見落としていた。全世代の権利証拠を集約するよう修正し、引継ぎでも引き続き保持する。読めない/不正な証拠は書き換えず、再付与を止める。
- **従来からある古い画面の競合（安全な範囲で改善）**: 2画面が受取待ちのまま開いている場合、先の画面で受取が保存されても後の画面が付与していた。マップ/Daily、ハート/ライフとも付与直前に証拠を再確認し、既に保存済みなら後の画面の付与を抑止する。世代をまたぐ画面でも同じ検査を行う。これは2処理が同時に検査を通過する競合への完全な排他制御ではない。
- **従来からの端末間制約（変化なし）**: 所持品・ライフ・報酬権利は公開プロフィール同期の対象外で、別端末は別の財布を持つ。比較では導入前/初版/修正版すべてで、別端末の同じ節目に各1件ずつ付与される。世代分離が新設したアカウント単位の重複ではなく、元からアカウント単位の報酬決済が存在しない構造による。
- **従来からの強制終了窓（変化なし）**: 所持数保存後、受取済み保存前に終了すると、再開時の再付与が起こり得る。比較でも全版で同じ結果を再現した。今回、保存順を逆転して報酬が消失するような変更はしていない。

別端末まで含む厳密な一度限りの付与や、所持数/受取済みの原子的な更新には、権威あるサーバー財布/報酬トランザクション、または所持品を含む回復可能な台帳設計が必要になる。既存財布を移行する追加設計が必要であり、今回の記録世代切替や未指示のサーバー適用では実施しない。


既存の旧バイナリ/旧タブは新しい権利再確認を実行しない。サーバールールは旧記録のリモート書込みを止められるが、端末内の財布の書込みまでは制御できない。これは従来のローカル財布方式の制約であり、今回の共通記録世代で所持品キーは変更していない。将来、所持品を含む完全リセットを行う場合は、旧版利用/旧タブの扱いも配布・移行手順に含める必要がある。


**引継ぎ先の別アカウント履歴も分離**: 移行先に残る旧アカウントの履歴は、そのままでは移行元アカウントの報酬を誤って抑止し得る。引継ぎ操作では、移行元ファイルの権利証拠を保存し、移行先の旧履歴キーを `ascent.reward-history-scope.v1` に参照除外として記録する。旧ファイルのバイトは削除・変更しない。新しいアカウントで作られる現行の記録と、移行元から受け取った権利は引き続き参照し、次世代でも継承する。移行先の旧権利を移行元の権利へ勝手に付け替えない。この参照範囲は引継ぎ処理のロールバック対象に含め、アカウント削除時にはゲーム保存と一緒に掃除する。
